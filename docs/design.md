## 1. What this actually is

A tiny, single-purpose Android app that flips two system flags and gives
one-tap access to the ADB wireless-pairing screen, surfaced primarily as
a **home-screen widget** (Microsoft Launcher) and optionally Quick
Settings tiles.

**The friction it removes.** On Android 15, Mahesh keeps Developer
options *off* so India banking/UPI apps behave, but needs it *on* for
`scrcpy`, sideloading custom-built apps, etc. Turning it back on today
means the 7-tap-on-build-number ritual, then Settings → System →
Developer options. Microsoft Launcher's built-in Settings shortcut only
deep-links as far as "System", not into Developer options.

**The key reframe (why an app is even possible).** The two things Mahesh
wants to toggle are each a single integer in `Settings.Global`:

| Toggle | Key | Values |
|---|---|---|
| Developer options | `development_settings_enabled` | `0` / `1` |
| Wireless debugging | `adb_wifi_enabled` | `0` / `1` |

Writing these from a third-party app needs the `WRITE_SECURE_SETTINGS`
permission. It is signature-level, so Android never shows a runtime
prompt — but it can be granted **once** over ADB to any sideloaded app,
after which the app writes the flags instantly via
`Settings.Global.putInt(...)`.

**Why this also kills the 7-tap ritual:** the taps are only needed
because `development_settings_enabled=0` makes the Developer options menu
*vanish*. Writing it back to `1` makes the menu reappear immediately — no
re-unlocking.

**The honest limit (toggle #3).** The "Pair device with pairing code"
dialog shows a 6-digit code + `IP:port` that are generated by the
system's adb pairing service. Only the system Settings UI surfaces them;
an app cannot render that dialog or read the code without root. So
toggle #3 is scoped down to **a one-tap deep link into the wireless
debugging / pairing screen**, saving the navigation, not reproducing the
dialog.

## 2. Goals & non-goals

**Goals**

- One home-screen widget (Microsoft Launcher) with, at minimum:
  - toggle Developer options (`development_settings_enabled`)
  - toggle Wireless debugging (`adb_wifi_enabled`)
  - a button that deep-links to the wireless-debugging/pairing screen
- A combined "banking-safe off" action that turns **both** flags off at
  once (see §3, rationale: some apps also flag active ADB, not just dev
  options).
- Smallest possible trust surface: **no `INTERNET` permission**, declare
  only `WRITE_SECURE_SETTINGS`. The whole point is an app Mahesh compiles
  and can audit, that physically cannot send telemetry.
- Live state reflected in the widget (show current on/off).

**Non-goals**

- Not on the Play Store. The ADB-grant onboarding is disallowed there;
  this is a personal sideload tool by design.
- No root. Must work on a stock, non-rooted Moto G05.
- Not reimplementing the pairing dialog / not reading the pairing code.
- No general automation engine. If a need is outside "flip these two
  flags + deep link", it's out of scope.
- Not trying to defeat or spoof banking detection — it leaves the device
  in exactly the state manual toggling would.

## 3. Key decisions (with rationale)

| # | Decision | Why |
|---|---|---|
| D1 | Build a custom app, not use an existing tool | Mahesh is hesitant to trust third-party apps (telemetry). An app he compiles himself, with no `INTERNET` permission, is the *smallest* trust surface of all options and is fully auditable. |
| D2 | Reject Tasker (and MacroDroid) | Overkill for two integer writes; large closed-source automation engine with network capability. Worse, its powerful features run via an **AccessibilityService**, which is exactly what India banking apps now detect and block. See §4 + §8. |
| D3 | Reject Loophole + a wireless-debugging widget | That's two separate third-party apps to trust — the opposite of Mahesh's goal — and still none of them surface the pairing screen. Good *fallback* only. |
| D4 | Grant `WRITE_SECURE_SETTINGS` once via ADB | Only non-root way. Survives reboots and app **updates**; lost only on uninstall+reinstall. Same one-time cost any option (incl. Tasker) would charge. |
| D5 | Toggle via `Settings.Global.putInt` on the two keys | These are the exact flags the OS and banking apps read; programmatic == manual, so banking checks can't tell the difference. |
| D6 | Provide a combined "banking-safe off" master action | Banking apps may flag active ADB (USB/wireless debugging), not only dev options. One action that zeroes both leaves a clean state. |
| D7 | Primary surface = home-screen widget; QS tiles optional | Solves the specific gripe that Microsoft Launcher's Settings shortcut won't go past "System". Widget buttons fire `PendingIntent`s into a receiver that writes the flags — reaching "past System" natively. |
| D8 | Scope toggle #3 to a deep link, not a reimplementation | The pairing code + `IP:port` come from the system pairing service; unreachable by a non-root app. Best achievable is jumping straight to the screen. |
| D9 | Name: **DevHatch** | Chosen by Mahesh. (A small hatch you pop open for dev work.) |

## 4. Roads not taken (and why) — the negative space

- **Tasker** — Mahesh used it years ago. Rejected: heavyweight, closed
  source, has network access, and its advanced actions use an
  accessibility service that India banking apps actively flag. For this
  task only its "Custom Setting → Global" action is needed (no
  accessibility required), so Tasker *could* be constrained safely — but
  that relies on Mahesh never enabling its accessibility service and
  trusting a big binary. The custom app gives that certainty by
  construction.
  Refs: Tasker Custom Setting userguide
  <https://tasker.joaoapps.com/userguide/en/help/ah_secure_setting.html>,
  XDA v5.2 custom-setting coverage
  <https://www.xda-developers.com/tasker-v5-2-immersive-mode-runtime-permissions/>.

- **MacroDroid** — Mahesh previously ran a pirated pro version; hasn't
  used it or Tasker in ~2 years. Same class of objection as Tasker, plus
  the pirated-binary trust problem. Rejected.

- **Loophole** (`shubhang-d/Loophole`, MIT, sideload) — does *exactly*
  toggle #1 as a QS tile, built for this same banking-vs-dev collision,
  and notably ships with **no network permission**. Good reference and a
  valid fallback, but it's a third-party binary and only covers one of
  the three wants. Ref: <https://github.com/shubhang-d/Loophole>.

- **Wireless Debugging Widget** (Play, `com.celestwatches.wireless
  debuggingwidget`) / **`afluffywaffle/adbwifi-toggle`** (GitHub) — each
  toggles `adb_wifi_enabled` the same way. Rejected as *additional*
  third-party apps. Refs:
  <https://play.google.com/store/apps/details?id=com.celestwatches.wirelessdebuggingwidget>,
  <https://github.com/afluffywaffle/adbwifi-toggle>.

- **Built-in Quick Settings developer tiles** (Developer options → Quick
  settings developer tiles → Wireless debugging) — one-tap from the
  shade, zero install. Rejected as the primary mechanism because the tile
  *disappears whenever Developer options is off*, so it can never
  re-enable the very thing Mahesh turns off for banking.

- **Pure deep-link shortcut** (no `WRITE_SECURE_SETTINGS`) using the
  `android.settings.APPLICATION_DEVELOPMENT_SETTINGS` action — would jump
  into Developer options in one tap, but only works when dev options is
  already enabled, so it can't solve the re-enable case. Useful only as
  the toggle-#3 deep link, not for toggling dev options itself.

- **Root / Magisk** — would allow reading the pairing code and more.
  Rejected: device is not rooted and rooting would itself break Play
  Integrity / banking apps. Antithetical to the goal.

- **Reimplementing the pairing dialog in-app** — impossible without root;
  the code/port live in the system pairing service. Hence D8.

## 5. Architecture

Everything is local; no services, no network.

**Components**

- `SettingsWriter` (util) — thin wrapper over
  `Settings.Global.getInt/putInt` for the two keys, with a guard that
  surfaces a clear message if `WRITE_SECURE_SETTINGS` isn't granted yet.
- `ToggleReceiver` (`BroadcastReceiver`) — receives widget-button
  `PendingIntent`s (actions like `DEVHATCH_TOGGLE_DEVOPTS`,
  `DEVHATCH_TOGGLE_ADBWIFI`, `DEVHATCH_BANKING_OFF`,
  `DEVHATCH_OPEN_PAIRING`), writes flags, then requests a widget update.
- `DevHatchWidget` (`AppWidgetProvider`) — renders current state and the
  buttons; rebuilt on every toggle so it reflects live values.
- *(optional, deferred)* `TileService`(s) — one per toggle, for people
  who also want the shade. Not required for v1.
- A small launcher `Activity` — status view + the one-time-setup
  reminder (the `adb` grant command), and a fallback set of buttons.

**Data model** — two integers in `Settings.Global`
(`development_settings_enabled`, `adb_wifi_enabled`). No app-local
persistence needed; the system settings *are* the source of truth. The
widget reads them on each update.

**Key flows**

1. *Enable dev mode:* tap widget → `ToggleReceiver` sets
   `development_settings_enabled=1` → Developer options menu reappears,
   `scrcpy`/sideload work.
2. *Banking-safe:* tap "banking off" → both flags set to `0` → identical
   state to manual off.
3. *Pair for wireless ADB:* tap "pair" → ensure `adb_wifi_enabled=1` →
   `startActivity` deep-link to the wireless-debugging screen → Mahesh
   taps "Pair device with pairing code" once to see code + `IP:port`.

**Permission** — `AndroidManifest.xml` declares **only**
`android.permission.WRITE_SECURE_SETTINGS`. No `INTERNET`. Granted once:

```
adb shell pm grant <package> android.permission.WRITE_SECURE_SETTINGS
```

(If multiple devices: `adb -s <serial> shell pm grant ...`.)

## 6. Dependency split

- **Ours (all of it):** widget, receiver, settings wrapper, optional
  tiles, status activity. Kotlin. No third-party runtime deps beyond
  AndroidX (and Compose only if used for the status screen — optional for
  a widget-first app).
- **System / AOSP (not ours, relied upon):** the two `Settings.Global`
  keys; the `WRITE_SECURE_SETTINGS` grant mechanism; the Settings app's
  wireless-debugging/pairing screen (deep-link target); the adb pairing
  service that generates the code.
- **Third-party:** none at runtime. Loophole is referenced only as prior
  art to read, not a dependency.

## 8. Operational & safety concerns

- **Banking detection — the part Mahesh asked to be sure about.** Two
  layers:
  1. *State:* flipping the flags leaves the device identical to manual
     toggling, so state-based checks are unaffected, and granting
     `WRITE_SECURE_SETTINGS` does **not** fail Play Integrity.
  2. *Accessibility / overlay:* India (and other) banking apps actively
     detect **active accessibility services** and **screen overlays** and
     block until disabled. DevHatch uses **neither**, so it sidesteps the
     one category banks hunt for — a concrete advantage over Tasker.
     Refs: bank notice listing accessibility + USB/wireless debugging as
     launch-time blockers
     <https://www.rhbgroup.com/-/media/Files/others/highlights/announcements/H20261026-1.pdf>;
     "detection is bank-controlled, can't be bypassed"
     <https://support.mobile-tracker-free.com/hc/en-us/articles/28700963753756-Banking-Apps-Detect-Android-Accessibility-Services>.
     (Content rephrased for compliance with licensing restrictions.)
- **Permission lifecycle:** the grant survives reboots and app updates,
  but is **lost on uninstall + reinstall**. The status screen should show
  the re-grant command so Mahesh isn't stuck after a reinstall.
- **Wireless debugging port rotates** after every reboot and Wi-Fi
  toggle — inherent to Android 11+ TLS wireless ADB, not something the app
  can pin. Ref: ADB Wi-Fi 2.0
  <https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0>.

## 9. Deferred / low-priority items

- Quick Settings tiles (one per toggle) — nice to have; widget is the
  priority. (D7.)
- Polished app icon / widget theming.
- Multiple widget sizes / layouts.
- Toggling USB `adb_enabled` as a separate control (banking-off already
  covers the risk via wireless; USB debugging is less of a day-to-day
  need). Revisit only if a specific bank still complains.
- A confirmation/undo affordance on "banking-safe off".

  `com.mahesh.devhatch`.
- **`minSdk` / `targetSdk`** — **RESOLVED:** `targetSdk 35`, `minSdk 26`
  (adaptive icons are API 26+, so this avoids legacy icon bitmaps; tiles
  are deferred anyway).
- **Exact deep-link target for the pairing screen on Moto G05.**
  **RESOLVED (2026-11-13, on-device).** No third-party app can open the
  dedicated Wireless Debugging screen on My UX. That screen is
  `WirelessDebuggingFragment`, hosted only by
  `com.android.settings.SubSettings`, which is **not exported** — even an
  adb-shell `am start` is denied (`Permission Denial … not exported from
  uid 1000`), and MtkSettings ships **no** `Settings$WirelessDebuggingActivity`
  alias (only the QS *tile* `DevelopmentTiles$WirelessDebugging`). Launching
  the exported base `.Settings` with `:settings:show_fragment` is ignored for
  an outside caller and lands on the Settings homepage.
  Best reachable target, implemented: open Developer options
  (`android.settings.APPLICATION_DEVELOPMENT_SETTINGS`) with the highlight
  extra `:settings:fragment_args_key = toggle_adb_wireless`, which scrolls to
  and flashes the "Wireless debugging" row — one tap from the sub-screen. The
  "Pair" tap routes through an invisible trampoline `PairingActivity` (an
  Activity, not the receiver) so the `startActivity` isn't blocked by
  background-activity-launch limits.
- **Does writing `adb_wifi_enabled=1` actually start the service on My
  UX** (advertise over mDNS), or does it only flip the flag and still
  need the UI to kick it? Verify on-device; if the latter, keep the deep
  link as the practical path for wireless ADB and treat the toggle as
  best-effort.
- **Include QS tiles in v1 or defer?** **RESOLVED:** deferred (§9).
- **Status screen in Compose or plain Views?** **RESOLVED:** plain Views,
  to stay light on a 4 GB device.
- **Does writing `adb_wifi_enabled=1` start the mDNS service on My UX?**
  Still unverified in isolation; the on-device check was complicated by the
  fact that the test connection runs *over* wireless adb, so toggling the
  flag drops the session. The "Pair" deep link remains the practical path
  regardless, so this is treated as best-effort per the original plan.

## 11. Suggested first steps (minimal slice)

1. New Android Studio Kotlin project, `targetSdk 35`. Manifest declares
   **only** `WRITE_SECURE_SETTINGS` (and the widget/receiver). No
   `INTERNET`.
2. `SettingsWriter` with `getInt/putInt` for the two keys + a
   not-granted guard.
3. One `Activity`: shows current state of both flags, has two toggle
   buttons + "banking-safe off", and displays the `adb grant` command.
4. Build, install, run the one-time grant:
   `adb shell pm grant <package> android.permission.WRITE_SECURE_SETTINGS`.
   Confirm the buttons flip Developer options and Wireless debugging.
5. Only then add the `AppWidgetProvider` + `ToggleReceiver` and place the
   widget on the Microsoft Launcher home screen.
6. On-device, discover the wireless-debugging/pairing component (§10) and
   wire the "pair" button.
7. (Optional/deferred) add `TileService`s.

Validate against the real goal: after a reboot, from the home screen,
Mahesh can enable dev mode in one tap, reach the pairing screen in one
tap, and return to a banking-safe state in one tap — without the 7-tap
ritual.
